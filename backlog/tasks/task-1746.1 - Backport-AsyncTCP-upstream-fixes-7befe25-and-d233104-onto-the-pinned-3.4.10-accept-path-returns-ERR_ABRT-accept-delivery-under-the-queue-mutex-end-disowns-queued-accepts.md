## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Follow-up of TASK-1746. otgw-firmware-09 checked upstream (2026-11-12): the pinned AsyncTCP 3.4.10 and the latest release v3.5.0 both do tcp_abort(pcb); return ERR_OK; in the tcp_accept callback (v3.5.0 AsyncTCP.cpp:1605-1610). Upstream main fixes it in 7befe25 'Report an aborted connection to LwIP as aborted' (ERR_ABRT), 4192390 'Build the accepted client's facade at delivery' and d233104 'Decide whether to deliver an accept under the queue mutex' (end() bumps _epoch, so accepts queued on a closed server are disowned: the reboot teardown race). Main is a large unreleased refactor, so do not track it whole. Robert's instruction to 09: check upstream, use it if fixed, otherwise patch; that counts as the OK for this library change (coordinator, 2026-11-12). AsyncTCP lives in .pio/libdeps, not vendored, so how we carry the patch is a build tooling decision: write a short ADR via adr-kit first, with ADR-186/ADR-187 (espMqttClient vendor and track) as precedent. Complements the prepareForReboot server.end() fix of TASK-1746 (beta.219).

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Claimed by otgw-firmware-95 (2026-11-13, coordinator assignment after the beta.219 post). Order: ADR first via adr-kit, no push until the coordinator says so.

Scope reduced to 7befe25 (95, 2026-11-13, advisor-checked, reported to the coordinator). Upstream clone: v3.4.10 (0f5b546) .. d233104 is 50 commits, 4 files +1325/-562 in src (shared impl objects b615bdc, 4d398a4, epoch/queue changes); d233104 and 4192390 do not apply to 3.4.10, so they would be our own rewrite against the old structure, without upstream review. 7befe25 (7befe25a549c) applies cleanly (offset -21) and fixes exactly this task's bug: v3.4.10 tcp_accept ends in 'tcp_abort(pcb); return ERR_OK;' (no-onConnect and client-allocation-failure fall-through). Checked: AsyncClient(tcp_pcb*) constructor and _free_event are identical in v3.4.10 and in 7befe25's parent, so the removed 'pcb already aborted' branch was dead code and _free_event of an ACCEPT event with client==nullptr is safe. d233104 deferred: its race (accepts queued on an ended server) is narrowed on our reboot path by the server.end()-first change of TASK-1746 (beta.219). Hashes (LF-normalized): .pio/libdeps/esp32-combo/AsyncTCP/src/AsyncTCP.cpp = upstream v3.4.10 = 10b7124eea6b9b0b8734d058d480219f81e2663ddfd958eb6be27241bac048da; v3.4.10 + 7befe25 = c786989e25a4372d7a0c855910d84a823c1e3a6e011c5b7a052a31214044e4e5. Mechanism: vendoring as ADR-186 would collide with ESPAsyncWebServer 3.11.2's transitive dependency ESP32Async/AsyncTCP ^3.4.10; PlatformIO installs lib_deps before SCons and the pre: scripts (platformio/run/processor.py:81), and libdeps/integrity.dat holds only the spec list, not file hashes (package/commands/install.py:273-290), so a pre-hook patch is not undone by an integrity check (source reading, to prove on a build). tests/test_reboot_listener_and_reason.py already reads the libdeps AsyncTCP.cpp. Drop condition: v3.5.0 lacks 7befe25; dropping needs an upstream release with it, and ESPAsyncWebServer 3.12 needs AsyncTCP 3.5.0, so that is a combined upgrade task, not a pin bump.

otgw-firmware-09's reading (2026-11-13, not proven, from the beta.215 backtrace and heap): 7befe25 only covers the client-allocation-failure and no-onConnect paths; at the 215 teardown free heap was 64736 B (requestDefer line 13:22:13.572), so an AsyncClient allocation failure is unlikely there, and the more likely cause is an accept on a server being torn down, which is d233104's case and which the TASK-1746 listener close (beta.219) narrows. Consequence taken into the ACs: AC3 (fault injection on the real tcp_accept) is the proof for 7befe25; the on-device repro in AC4 tests the listener close and is a regression check for the patch, not its proof. ADR number ADR-232 confirmed free by the coordinator (all worktrees and git log --all, 2026-11-13).
