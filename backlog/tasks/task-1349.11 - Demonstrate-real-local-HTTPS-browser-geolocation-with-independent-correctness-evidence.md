## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The maintainer's decisive proof is a real local browser using native ESP32-S3 HTTPS to obtain the correct physical location. Passing unit tests, injected coordinates and a proxy cannot establish this.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A clean real-browser session opens the ESP32's trusted HTTPS application directly; URL/device identity, TLS issuer/SAN/fingerprint and window.isSecureContext=true are captured without error bypass.
- [ ] #2 The browser location provider is real: permission is granted by the operator; no automation geolocation override, stub, DevTools sensor simulation or prerecorded response is used.
- [ ] #3 With client and ESP32 co-located at a pre-established reference site, returned accuracy is at most 100 m and Haversine distance to the independent reference is at most 100 m; both values and reference uncertainty are recorded.
- [ ] #4 The real UI confirms the detected pair, sends it by HTTPS, and reads the same saved values after reboot within rounding tolerance; correct Open-Meteo request coordinates are verified without claiming weather-data accuracy.
- [ ] #5 At least one physical mobile browser and one desktop browser are exercised; each target's result is labelled passed, failed or unavailable. One eligible real device/browser pass is the minimum functional proof.
- [ ] #6 Denied permission, wrong/low-quality result, untrusted certificate and plain-HTTP controls are evidenced; a wrong location or provider limitation is reported as failure/inconclusive, never a pass.
- [ ] #7 A durable redacted evidence bundle has timestamps, build hashes, browser/OS versions, screenshots or recording, network/security evidence and independently reviewable correctness calculation; exact personal coordinates stay in restricted local evidence.
<!-- AC:END -->
