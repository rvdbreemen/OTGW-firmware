## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Field finding from indigo_light's beta.350 capture (real Viessmann Vitodens, SAT on, simulation off; archived at RvdB/OTGW-field-data/indigo_light/20261116-144953/analysis/; analysis by comms 92, Sergeant D DM 1571924364050432032). Between 16:17 and 16:39 (tester local time) SAT switched modes four times while the flame burned without a break (16:18:36-16:51:12, 1955 s): 16:17:58 PWM (enter); 16:19:58 continuous ('flame on and request 38.1 above flow 26.1 for 60s'); 16:30:28 PWM (flow 42.4 >= 40.9 + 1.5 for 30 s); 16:32:28 continuous (request 41.4 above flow 35.2 for 60 s); 16:35:28 PWM (flow 41.9 >= 39.5 + 1.5); 16:37:28 continuous (request 39.0 above flow 37.1); 16:39:28 PWM (flow 40.7 >= 37.9 + 1.5) until PWM OFF 16:50:28. The control setpoint swings with the mode (e.g. 55.0 in a PWM ON phase, 38.1 in continuous). Rules involved: enter = TASK-1888 / entry 327 and 379 (flow >= request + 1.5 C for 30 s, SATcycles.ino:1393); exit = ADR-236 (Proposed; entries 339 and 342: flame on and request above flow for 60 s). Thermo-nova (pin 7beaaf5) uses a wide gap: enter flow >= request + 3.0 for 60 s (heating_control.py:288-296, const.py:21, cycles/const.py:10), exit flow <= request - 3.0 for 180 s (heating_control.py:335-343, const.py:22). Sergeant D decides whether this is acceptable and what the fix is (question Q-2005a with the scope line); no change before his answer.

Why it ping-pongs (indigo 16:17-16:39, one burn 16:18:36-16:51:12, inference from the code plus the SATTICK values): in a PWM ON phase the request sits above a lagging flow, so request > flow for 60 s fires OUT; in continuous the setpoint follows the PID (about 38-41 C) and the boiler at its minimum output overshoots, so flow >= request + 1.5 for 30 s fires IN. The two thresholds have no gap between them (in at request + 1.5, out at any request above the flow), so each fires within 2-5 min. A minimum dwell time in a mode: NOT FOUND in thermo-nova (grep for dwell, cooldown, last_switch, hold in heating_control.py, pwm.py and cycles/*.py: no hits) and not in the firmware; thermo-nova's separation comes only from the wide gap (+3.0 C / 60 s in, -3.0 C / 180 s out). Stale comments found: SATcontrol.ino:8291 still says fOvershootMargin 2.0 C / 60 s and :8313 says 180 s underheat, while the code uses fPwmSwitchMargin / 30 s and 60 s; fix those comments with the implementation.

2) PER OPTION, what changes. A (keep): no code change; document the flip-flop as known behaviour for the field runs. B (no PWM re-entry in the same burn): a file-static flag in SATcycles.ino (for example _sat_pwmLeftThisBurn), set where satCycleCheckPwmExits() switches to continuous with the flame on (:1462; the saturation exit :1475 too only if Sergeant D says so: open sub-question), cleared on flame off in satCycleOnFlameChange(false) (SATcycles.ino:1024) and when SAT stops or restarts; satCycleCheckOvershootSwitch() does not switch while the flag is set (a gate next to :1378 that also clears _sustain_overshootRunning, so a qualifying run after the flame-off edge starts fresh). Open sub-question for B: may the 3.5 C flame-out fail-safe (:1399, TASK-1762, entries 288/289) still enter PWM in the same burn? Recommendation: yes, it guards a flame-out case, not the normal switch. The PWM-first start (satPwmFirstStart, SATcontrol.ino:4019) is not affected: a new burn begins after a flame-off edge, which clears the flag. Thermo-nova has no counterpart for B (not found in the code; its gap does that job), so the ADR says so; a new short ADR amends ADR-249 or ADR-236. C (thermo-nova exit): SATcycles.ino:1458 becomes flow <= request - 3.0 (a new constant, thermo-nova's UNDERSHOOT_MARGIN_CELSIUS) without the satIsFlameOn() term (thermo-nova checks heater ON in its gate, :317-319), and SAT_UNDERHEAT_SUSTAIN_MS at :47 goes from 60000 to 180000; ADR-236 (Proposed) is withdrawn or superseded and entries 339/342/350 are partly reversed (a new entry). Risk of C: a PWM ON phase that never reaches the request (oversized boiler at its minimum) stays in PWM longer before continuous.
