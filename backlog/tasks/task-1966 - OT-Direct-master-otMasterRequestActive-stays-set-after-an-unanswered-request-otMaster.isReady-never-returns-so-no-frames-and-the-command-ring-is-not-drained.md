Second, unverified candidate: setDelay() (OpenTherm.cpp:389-395) compares 'newDelay > delayTimestamp' without wrap safety; micros() wraps every ~71.6 min. # TASK-1966 analysis (session 95, 2026-11-15, code read on origin/dev 3e29faa63; not yet reproduced) ## Facts from 09 (.61, beta.298, master mode) - ~08:10 after the bench restore (switch to master, then SW=0 / SH=0 / OT=- / MM= close together): no R/B frames. - REST commands 202, then 503 "queue full"; OT=7.6 no override, PR=T no reply. - 11:03: the ring took 9 posts again, but OT=7.6 did not run and no `OTD: cmd` line appeared. - Simulation ruled out (satsimulation/satenabled false, otgw/sensor sim false, health simulation_active false, 0 SIM lines). ## Code facts 1. Only `otdCmdTextDrain()` moves the ring tail (OTDirect.ino:3603). `loopOTDirect()` calls it only with `otMasterRequestActive` false (:2623). On the loop task `addCommandToQueue()` drains first only when `otdCmdTextMustWait()` is false, i.e. not (queued && request in flight) (OTGW-Core.ino:3920-3928). 2. `handleOTDirectCommand()` logs `OTD: cmd` unless `len < 3` (:3697-3701); `otdCmdTextPush()` refuses len <= 0 or > PIC_CMD_MAX_LEN (:3575). No silent drop between drain and the log line. 3. `otMasterRequestActive` is set only from `otMaster.sendRequestAsync()` (:1901) and cleared only at the end of `handleMasterResponse()` (:2086), which runs only when `otMaster.isReady()` (:2631). 4. Library (src/libraries/OpenTherm/src/OpenTherm.cpp): `isReady()` = rx IDLE && tx IDLE && delay passed (:136). `process()` times out only `WAIT_RESPONSE` (1 s, :457-460); a non-IDLE rx becomes IDLE after 5 ms. `TX_DATA` is set in `sendFrame()` before `gptimer_start()` (:220-221) and leaves only through the last tick of the timer ISR (:177-184). `end()` deletes the timer and does not reset txStatus (:547-565); `begin()` resets only rxStatus. 5. The mode switch calls only `otSlave.begin()/end()` (separate instance and timer), never `otMaster` (:3223-3262). `otMaster.end()/begin()` only in GW=R (:4222-4226, runs from the ring with the flag false) and at boot (:1323). ## Candidates A. Master stuck in TX_DATA (flag stays true): explains "no frames" + ring full + 503. Does NOT explain 11:03 (the ring drained, so the flag was false then). Trigger unknown: no code path found that stops the master timer mid-frame. B. Flag false but the library never ready: `sendMasterRequestAsync()` returns false at `!otMaster.isReady()` (:1897) every pass, so the flag stays false, the drain runs, commands run. Explains 11:03 draining, but then `OTD: cmd` WOULD be logged; 09 saw none. So B alone does not fit either. C. The posts at 11:03 did not reach this ring (another REST route, or the ring indices out of step). Not found in code. Open: no candidate explains all four facts. The missing `OTD: cmd` line at 11:03 is the key fact; it needs a capture. ## Fix (independent of the trigger) - Watchdog in loopOTDirect (our code, public library API only): `otMasterRequestActive` set for longer than 1500 ms since `sendRequestAsync` without `isReady()` -> log `OTD: master request stuck ... -> restart`, `otMaster.end(); otMaster.begin(masterISR);`, flag false, origin reset, counter `iMasterStallRecoveries` (state.otd). Also: `!otMaster.isReady()` continuously for > 1500 ms with the flag false -> same restart (covers B). - Diagnostics so the next stall shows its state: REST device/info (or health) gets the flag, its age, the ring head/tail/dropped and the recovery counter. ## Test design (red on 3e29faa63, green on the fix) - Host harness on the real `loopOTDirect()` slice + `sendMasterRequestAsync()` + the ring block, with a fake OpenTherm class whose `isReady()` can be forced false (stuck TX_DATA) and whose `end()/begin()` make it ready again. - Case 1 (A): send a request, force stuck; REST-thread posts 8 commands -> old: flag stays true after 5 s, the 8th push is Dropped (503), no command runs; fix: within 1.5 s a recovery log line, the flag false, the queued commands run in order, a new request goes out. - Case 2 (B): library not ready with the flag false for 5 s -> old: no frame ever; fix: restart after 1.5 s, frames resume. - Case 3: normal traffic (ready within 1 s, a 1 s TIMEOUT answer) -> no restart, counter 0 (no false trigger).
