2026-11-08 code analysis (read-only, dev d1c6721da; the two gate claims spot-checked by hand):
- MQTT gate is 16 KB, not 8 KB: espMqttClient Packet.cpp:315 refuses packet buffers when the largest block is < EMC_MIN_FREE_MEMORY=16384 (Config.h:32, not overridden in platformio.ini). PINGREQ is gated too (Packet.cpp:301), so keepalive dies below 16 KB, leading to reconnect bursts. 'MQTT packet not queued' therefore starts below 16 KB maxblk.
- Most REST 503s are not the 8192 gate: restEffectiveInflightCap() (restAPI.ino:55) serializes to 1 in-flight request below 16000 maxblk, and webFileGateTryAdmit() (:99) likewise. Only debug, device/info, diag download, graph/history and sat/status have the 8192 gate. Counters hd_rest_503 / hd_webfile_503 / hd_webconn_503 tell the causes apart.
- Ranked fragmentation suspects: (1) AsyncResponseStream grows in exact-shortfall resizeAdd steps (WebResponses.cpp:927-932) on otmonitor (polled) and others; (2) WS session setup leaves request debris between long-lived AsyncClient/pcb and WS client (AsyncWebSocket.cpp:998-1004), repeated on every 5 s reconnect; (3) make_shared OTGWState snapshots live for the whole chunked response (SATcontrol.ino:4230, restAPI.ino:2225); (4) WS textAll per OT line, freed only on ACK (up to 5 s, 32/client); (5) MQTT publish: temp buffer, then outbox node+data, then temp freed, leaving a hole under the outbox; (6) BLE only if bBleRiskAck on no-PSRAM, lazy init from loop(), per-advert allocations; (7) diag recorder about 4.8 KB lazy, off by default; (8) lwIP pcb per Connection: close poll (plausible).
- Still readable when stuck: GET /api/v2/device/time (freeheap, maxfreeblock, internal_maxblk), telnet D. The hd_* dip snapshot in device/info is gated off below 8192, so poll it while maxblk is still above 8 KB.
- Not verified: core cbuf::resize behaviour, sizeof(OTGWState), sdkconfig MSS/TLSF, NimBLE footprint.

2026-11-08 17:37: the open points, closed by reading code and the ELF (no device; ELF = wt-1730 build/OTGW-firmware-esp32-combo-2.0.0-beta.147+d63a128.elf, xtensa-esp32s3 nm + gdb):
- sizeof (beta.147, target): state (OTGWState) 0x880 = 2176 B (nm). SatStatusSnap 2272, DebugDumpSnap 2328, DeviceInfoSnap 2720, DiagDownload 652, state.sat 1224, AsyncResponseStream 144, AsyncWebSocketClient 168, cbuf 16 (gdb sizeof). So every sat/status, debug and device/info request holds a 2.3-2.7 KB make_shared block (+ control block) for the whole chunked response.
- cbuf::resize (core 3.3.5, cores/esp32/cbuf.cpp:75-133) does not realloc. It calls xRingbufferCreate(newSize) (:91, which is calloc(Ringbuffer_t) + malloc(newSize): esp_ringbuf ringbuf.c:951-952, IDF 5.5.1 source package), then malloc(bytes_available) as temp (:100), copies, frees the temp (:123), then vRingbufferDelete(old) (:128). Peak per resize is about old + new + content, roughly 3x the response so far, in 3 blocks of different lifetimes.
- AsyncResponseStream growth (ESPAsyncWebServer 3.11.2 WebResponses.cpp:926-941): initial cbuf 1460 B (RESPONSE_STREAM_BUFFER_SIZE); every write that does not fit calls resizeAdd(exact shortfall). JsonEmit (jsonEmit.h:119-162) prints keys, quotes, separators and values as separate print() calls of 1-20 B, so past 1460 B nearly every print is a full ringbuffer recreate.
- otmonitor: sendOTmonitorV2 (restAPI.ino:3004-3113) emits 38 fields via that path. v2.js:3309 polls it every 2000 ms per tab. ESTIMATE (not measured): ~3 KB response, ~600-700 prints, ~300 resizes per request, so with 2 tabs ~300 recreate cycles/s of steadily growing 1.5-3 KB blocks. Each freed old buffer is just too small for the next request, which is the textbook staircase fragmentation pattern. Strongest suspect so far.
- Still not verified: that the prebuilt framework-arduinoespressif32-libs ringbuf matches the IDF 5.5.1 source; the real otmonitor size and print count (needs one GET or a host run of the JsonEmit path); sdkconfig/TLSF; NimBLE footprint.

2026-11-08 17:52: fix candidate (preventive) in worktree wt-1736 on branch lane-1736. It is staged but NOT committed: the pre-commit hook requires a _VERSION_PRERELEASE bump, and the beta number is the coordinator's call.
- What it does: the polled AsyncResponseStream endpoints (otmonitor, device/time, health, BLE roster, weather) get a size class. The class learns its body size (high-water mark, rounded up to 512 B with +12.5 %, cap 8 KB), and the next response presizes via beginResponseStream(ct, size) (ESPAsyncWebServer 3.11.2 ESPAsyncWebServer.h:748). With maxblk < hint + 4096 it keeps the 1460 B default, because a failed upfront cbuf leaves size 0 (cbuf.cpp:53-54). A body longer than the hint still works: the tail grows as before. restFinalize logs 'REST stream size: class=... len=... cap=... hint=...' once per newly learned size, or on a presized overflow. That line is the per-endpoint measured body size. Heap-tight fallbacks are counted only. No library edits.
- Scope: settings, sat/status, device/info and debug are already restSendChunked (no cbuf), so they are untouched.
- Evidence: test/host/build_and_run_stream_size.ps1 (MSVC). Sizing rules are sliced from webServerCompat.h; part B models the library growth rule. 2026-11-09 AC1, explained from the code (session 4c). Every polled REST stream (otmonitor, BLE roster, weather) started as a 1460 B AsyncResponseStream and grew on each JsonEmit print that did not fit: ESPAsyncWebServer 3.11.2 WebResponses.cpp:926-943, write() calls _content->resizeAdd(len - room) for the exact shortfall. In the Arduino-ESP32 core, cbuf.cpp:71-72 turns that into resize(size() + add), and resize (cbuf.cpp:75-126) first creates a NEW ring buffer of the full new size (xRingbufferCreate, :91) while the old one is still alive, then mallocs a temporary copy of all buffered bytes (:100), copies, frees the copy (:123) and only then deletes the old ring (:124-126). JsonEmit prints 1-20 B at a time, so past 1460 B nearly every print repeats this. Measured with the real cbuf and the real write() in the new host test: one 3061 B otmonitor-like body makes 398 ring buffers of 398 different sizes (1460..3061 B, each a few bytes larger than the last), 397 temporary copies, and a transient peak of 9181 B live (old ring + new ring + copy, 3 x the body). Two tabs poll otmonitor every 2 s each, so this runs several hundred times per minute, interleaved with lwIP pbufs, WebSocket frames and MQTT buffers allocated by other tasks. Each cycle frees a block of size N right after allocating one of N+k, which leaves holes of 1.5-3 KB between longer-lived allocations: free memory stays near 31 KB while the largest free block shrinks. Below 8192 B the low-heap gates (the 8192 B maxfreeblock gate on sat/status, graph/history, device/info, restAPI.ino; the cap-1 clamp under 16000) answer 503, which is the 'every REST call 503 low heap' lock-out of beta.146-148 at maxblk 7668. The hole mechanism is inference: the TLSF allocator on the device was not modelled or traced. The presize (44d6ef686, beta.155: otmonitor 4096, BLE roster 3072, weather 2048, kept at 1460 when maxblk < presize + 4 KB) makes each poll one allocation of the same size. The 7668 B lock-out did not come back on bench .61 in 2026-11-09 runs: beta.159 two-tab red run 08:11-08:31 maxblk min 12276; beta.160 08:33-09:39 min 13300.
