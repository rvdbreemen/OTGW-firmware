## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found with the TASK-1774 RTC probe (otgw-bench-tester 09, .63, 2026-11-14 04:50-04:57, 09 scratchpad b1774\). A freshly flashed image (img=PENDING_VERIFY) that panics did not roll back on the first reset: ota_0 booted again and reported img=ABORTED reset=4; only the second panic rolled back to safeboot (/info app_rolled_back=true). safebootMarkAppValid() (OTGW-ModUpdateServer-esp32.h:154-161) confirms only PENDING_VERIFY, so the app running as ABORTED never confirms itself, and any later reset (planned restart, settings change, FS OTA, crash) rolls it back to safeboot. Fits beta.217 on .63 (2026-11-12): panic during an FS write, unit came back on main, rollback only after the 2nd FS upload (TASK-1774 notes). Reading (not verified): local framework-espidf bootloader_utility.c:396-405 marks PENDING_VERIFY as ABORTED at the next boot; :407-416 falls back to factory only when both otadata entries are invalid, else :440-443 boots the active valid entry, ota_0 with one OTA slot. That implies a second, still valid otadata entry; who left it is not shown, and the pinned bootloader is a precompiled binary. Pending proof: esptool read_flash of otadata (0xE000, 2 x 4 KB) on .63 in three states (fresh probe flash, after the 1st panic, after the rollback), by 09. Any change to when an image confirms itself changes ADR-191 rollback behaviour: maintainer decision, not decided here.

Entry = ota_seq / state / crc (crc = crc32(seq, init 0xFFFFFFFF), checked). Decoded: REF (beta.317 running, valid): [0] seq=1 VALID, [1] seq=1 NEW, both crc ok. A (probe1774+370b324 app OTA through safeboot, first boot, telnet RTCPROBE img=PENDING_VERIFY reset=3): [0] seq=1 PENDING_VERIFY, [1] seq=1 NEW. B (after the 1st reset; the probe booted again, RTCPROBE img=ABORTED reset=11): [0] seq=1 ABORTED, [1] seq=1 PENDING_VERIFY. C (after the 2nd reset): [0] seq=1 ABORTED, [1] seq=1 ABORTED -> safeboot /info app_valid=false app_rolled_back=true. D (317 uploaded through the safeboot updater, confirmed): [0] seq=1 VALID, [1] seq=1 ABORTED. Mechanism shown: BOTH otadata sectors hold a CRC-valid entry with the SAME seq=1 (both select ota_0, the only OTA slot). At the reset the bootloader marks the PENDING_VERIFY entry ABORTED, then takes the other entry (NEW, same seq, ota_0) and turns it into PENDING_VERIFY, so the same image gets a second boot while esp_ota reports img=ABORTED for the running app; only when both entries are ABORTED does the bootloader fall back to factory (safeboot). The second NEW entry is left by an earlier write (REF already had [1] NEW next to [0] VALID; after D [1] stays ABORTED and [0] is rewritten seq=1 VALID), i.e. the updater/OTA path writes seq=1 into one sector and leaves a same-seq copy in the other instead of incrementing the seq. Which code writes the [1] NEW copy is not shown by the dumps (needs a dump right after a safeboot upload, before the first boot). Restore: .61 back on beta.317+984d60a (manual safeboot upload, ota_flash refuses from safeboot), settings.ini diff vs before empty, no crashlog, bootcount 749 -> 753. 2026-11-15 ba code reading for AC1 (local framework-espidf; single source, the pinned bootloader is a prebuilt binary of the same IDF line, not checked against it). bootloader_utility.c:396-404: at every boot each otadata entry in PENDING_VERIFY is rewritten as ABORTED. bootloader_common_loader.c:71-79: an entry is invalid when ota_seq is 0xFFFFFFFF or its state is INVALID or ABORTED; :81-90 the active entry is the valid one with the highest seq. bootloader_utility.c:440-443: boot_index = (seq-1) % app_count, and with ONE OTA slot (app_count 1) every seq maps to ota_0. Reading: after the safeboot updater writes ota_0 it sets a new entry (seq N, NEW -> PENDING_VERIFY at the next boot). A panic before the health gate leaves it PENDING_VERIFY; the next boot marks it ABORTED and, if the OTHER sector still holds an older VALID entry (seq N-1, from the previous image), selects that one, and (N-2) % 1 = 0 boots ota_0 again: the NEW image, now running without a PENDING_VERIFY entry. esp_ota_get_state_partition(running) then reports the state of the highest-seq entry for ota_0, the ABORTED one, and safebootMarkAppValid() (OTGW-ModUpdateServer-esp32.h:155-162) does nothing. Not explained by this reading: why the second panic then rolled back to safeboot (the VALID older entry would keep booting ota_0). Possibly the app or esp_ota on an ABORTED running image invalidates the other entry; to verify. Dumps for AC1 (09, .63): esptool --port COM8 read_flash 0xE000 0x2000 otadata-<state>.bin in the three states (after the probe flash and first boot, after the 1st panic, after the rollback); per 4 KB sector the first 32 bytes are ota_seq (u32 LE), seq_label[20], ota_state (u32: 0 NEW, 1 PENDING_VERIFY, 2 VALID, 3 INVALID, 4 ABORTED, 0xFFFFFFFF UNDEFINED), crc (u32). Options for AC2, to put to Robert once the dumps confirm it: A) safebootMarkAppValid() also confirms when the running image reports ABORTED and the health gate passed (mark valid via esp_ota_mark_app_valid_cancel_rollback works only on PENDING_VERIFY, so it needs esp_ota_set_boot_partition(running) to write a fresh VALID entry); B) an ABORTED running image hands over to safeboot at once (it failed its first boot); C) leave it (the next reset rolls back as observed).

2026-11-15 cause (09's dumps on .61, scratchpad t1919/, plus the IDF source): with ONE OTA slot esp_rewrite_ota_data() (app_update/esp_ota_ops.c:575-590) computes the new seq as (0+1)%1 + i*1 with the smallest i >= seq, i.e. the SAME seq, and writes it into the other sector as NEW. The safeboot updater calls esp_ota_set_boot_partition() twice per update (safeboot/src/main.cpp:185-192 at its start after the handover erased otadata, and Update.end(true) after the upload): E [0] seq1 NEW|[1] erased -> G [0] seq1 PENDING|[1] seq1 NEW -> H [0] VALID|[1] NEW. A failure in G: the bootloader marks [0] ABORTED (bootloader_utility.c:396-404) and boots [1] (equal seq picks sector 0 while both valid, bootloader_common_loader.c:144-168; [0] invalid now) = the same image a second time, reporting ABORTED. Fix (b), coordinator agreed as a plain bug fix: safebootDropStaleOtadata() early in setup() erases the otadata sector the bootloader does not boot from, judged exactly as the bootloader does (valid = seq != 0xFFFFFFFF, state not INVALID/ABORTED, CRC32 of seq ok; highest seq, equal -> sector 0), only when that sector holds something (no wear per boot), only on the safeboot layout with one OTA slot; one telnet line 'otadata: erased stale sector ...'. safebootMarkAppValid() unchanged. Works on every existing unit through a normal OTA; the safeboot updater (USB only, ADR-191) is not changed.
