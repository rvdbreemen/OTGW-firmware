## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Found by otgw-docs while writing the OTGW32 documentation (TASK-3115), coordinator 2026-11-27. An OTGW32 owner confirmed (#beta-testing 1575787624054919179): W5500 Ethernet uses SPI on GPIO 11,12,13,14,15 and 1-Wire is connected to GPIO 4. Firmware at origin/dev: 1-Wire is PIN_1WIRE 4 (src/libraries/Platform/src/boards.h:82) but no source file reads it; the Dallas pin is settings.sensors.iPin with default 10 (Sensorstypes.h:23), and 10 is PIN_STEPUP_ENABLE (boards.h:79), a reserved board pin, so sensors_ext.ino:308-311 refuses it and starts no sensors until the user sets the pin; GPIO 4 is not reserved (OTGW-firmware.h:1058-1067). The S0 counter default 12 (S0types.h:22) equals PIN_SPI_SCK 12 and the GPIO output default 16 (Outputstypes.h:22) equals PIN_SPI_RST 16 (boards.h:90-91): both collide with the W5500. A comment above LEGACY_S0_PIN in OTGW-firmware.h says the free OTGW32 header pins are not documented yet. Owner: otgw-dev. Open question to the owner of the hardware: which header pins are free for the S0 counter and the GPIO output on the OTGW32.

DESIGN. Honest caveat for AC3: writeSettings saves the key on every save, so 'stored 10' cannot tell 'never chose' from 'saved the default'; on the OTGW32 map 10 is a reserved pin that never worked, so moving it loses nothing. (2) S0: on the OTGW32 map a stored legacy 12 (W5500 SCK) becomes UNSET until the hardware owner confirms the DI pad (GPIO 5, net SWR); S0 stays in settings/UI/REST/MQTT, default 'off', the user chooses a pin, the refusal for reserved pins stays. (3) GPIO output: a runtime predicate boardHasOutputPin(ComboPinMap) (OTGW32 false, Classic maps true), a function and not a compile-time macro because the combo image picks the board at boot (HAS_RUNTIME_HW_DETECT, boards.h:316-320; same reason as boardPinReserved). On the OTGW32 map: initOutputs does nothing and says so once; updateSetting for the output settings is refused with a debug line (the REST/MQTT writers must not enable an output on a board without a pin); the device/info JSON gets has_output_pin (true/false; webui hides the output group on false, absent = shown); the settings echo keeps the keys so old clients do not break. LED blink is not touched. (4) Docs: docs/manuals ch11 11.6 en and nl, docs/hardware/PINOUT.md, MQTT.md/REST docs for has_output_pin.
TESTS (host, real code, red first): extend the TASK-1698 harness tests/test_legacy_pin_defaults.py and tests/test_board_pin_reserved.py: per map the migrated defaults; stored non-legacy pins never move (4, 15, 5, 7, 40); no migrated default is a reserved pin of its map; OTGW32: Dallas 10 -> 4, S0 12 -> -1, output unchanged by migration but boardHasOutputPin false; Classic: unchanged results of TASK-1698; REST text checks for has_output_pin and the range metadata. 2026-11-27 FINDING (coordinator asked, otgw-docs, code at origin/dev 8e518557f). (a) No repo source says which OTGW32 GPIO is exposed on a terminal block, pad or header: boards.h:56-97 and docs/hardware/PINOUT.md section 2 list signals per GPIO only (OT master IN 21 / OUT 1, OT slave IN 6 / OUT 7, I2C 17/18, 1-Wire 4, step-up enable 10, bypass relay 47, W5500 SPI 11 to 16, LEDs 2/8/48, buttons 0/9); OTGW-firmware.h:1087 says the free header pins are not documented yet; the only terminal-block text (ch02:72) is about the Classic. (b) Which of the 10 terminal-block pins map to GPIOs is not documented (inference only, not verified: the OT lines go through the OT interface to the thermostat and boiler terminals). The hardware owner said the 10-way terminal block is what he understands by header and that S0 and output are not known to be supported on the OTGW32. (c) S0 and GPIO output are compiled into the OTGW32 build with no HAS_* gate, default OFF (S0types.h:21, Outputstypes.h:21 bEnabled false), defaults 12 and 16 (S0types.h:22, Outputstypes.h:22) equal W5500 SCK and RST; when enabled with those pins the firmware REFUSES them (s0PulseCount.ino:42, outputs_ext.ino:26, sensors_ext.ino:308, boardPinReserved OTGW-firmware.h:1058-1067), so Ethernet cannot be broken by the defaults or by a reserved pin; the remaining risk is a pin outside the reserved list that is wired to something else (GPIO 4 is not in the list). RECOMMENDATION (otgw-docs, decision with the coordinator and Robert): hide or disable S0 and GPIO output on the OTGW32 board type behind a HAS_* flag (settings, UI, MQTT) until the hardware owner documents free pins; the Dallas half stays: default pin 4 on the OTGW32. AC1 is therefore rewritten in practice: S0 and output: flag off on OTGW32 (or board-specific defaults once pins are known); Dallas: default 4.

2026-11-27 CODE CHECK of GPIO 5 and DI (origin/dev c54219591 and later): the firmware does not use GPIO 5 anywhere (grep over src/OTGW-firmware and boards.h: no PIN define, no read; the only hit for 'GPIO 5' is an unrelated ESP8266 I2C comment in OTGW-firmware.ino:305); the reference firmware's NODO pin block (other-projects/OT-Thing-OTGW32/Firmware/include/hwdef.h:12-37) has no GPIO 5, SW or DI definition either, and hwdef.h:19 says 'GPIO_BYPASS_RELAY 47 /* not connected on Nodo but need for compilation */' (relevant to the question whether net REL on GPIO 47 is a relay: the reference says the relay is not connected on that board; the owner says hardware version 1.1 has an optional relay not fitted). The OT-Direct bypass/switch code does not read a switch input (OTDirect.ino has the bypass relay output only, compiled out). S0 code: s0PulseCount.ino:22-50 sets the pin INPUT_PULLUP and attaches a FALLING interrupt with a debounce time (settings.s0.iDebounceTime): the ESP32-S3 can take that interrupt on any GPIO, so the current code would count pulses on GPIO 5 if the DI pad is a plain 3.3 V input with a usable pull-up; GPIO 5 is not in boardPinReserved (OTGW-firmware.h:1058-1067) and inside the accepted range (OTGW-firmware.h:1105-1112), so the setting accepts 5 today. NOT KNOWN: what DI is wired to (protection, level shifting, pull resistor, polarity), and whether the owner intends it as a pulse input. I did not verify from the datasheet whether GPIO 5 has any strapping role on the S3 (from memory the strapping pins are 0, 3, 45 and 46; not verified here).
