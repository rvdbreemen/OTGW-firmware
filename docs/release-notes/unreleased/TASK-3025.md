### Web UI live connections are dropped cleanly when the unit runs out of memory (TASK-3025)

When a unit is almost out of memory (free heap under 3 KB) it frees memory by dropping the browser connections that stream the
live log (the `/ws` connections). Before this beta it asked each browser to close politely; a browser or tab that did not answer
could stay half-open for about a minute and keep holding memory. Now the unit drops those connections at once, and an open web UI
tab reconnects by itself within about 10 seconds. Nothing changes for a unit that is not out of memory.

- What you may notice: a live view that blinks and reconnects once after a memory emergency. The unit does not restart for this.
- New counter in `GET /api/v2/device/info`: `hd_ws_recovery_abort` (how many live connections were dropped this way since boot).
- Beta builds only: telnet key `K` holds the free memory down on purpose for a few minutes to test this. Do not press it on a unit
  you rely on; it is not in release builds.

How it was tested: host tests of the real code against a simulated connection list, and a bench run on a unit without extra RAM
(the kind of board where this memory emergency happens in the field) with two to three live tabs open, three runs per build,
before and after the change. A fault in this path would show as a restart or a crash entry in `GET /api/v2/device/crashlog`;
please report one with the capture.

<!-- VARIANT B: the K bench ran only on .63 (a board WITH extra RAM); label it exactly like this, no "tested on the affected board" -->
How it was tested: host tests of the real code against a simulated connection list, and a bench run on a unit that has extra RAM,
with two to three live tabs open, three runs per build. The memory emergency was forced on purpose (telnet key `K`), so the
mechanism is proven: every open live connection is dropped exactly once. The margins on a unit WITHOUT extra RAM, where this
emergency happens in the field, were not measured yet: that is what we ask testers with such a unit to watch. A fault in this
path would show as a restart or a crash entry in `GET /api/v2/device/crashlog`; please report one with the capture.
