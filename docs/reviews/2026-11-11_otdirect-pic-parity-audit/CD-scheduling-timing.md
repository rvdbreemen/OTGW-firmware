# TASK-1795 audit, areas C (message scheduling) and D (bus timing and error handling)

Read-only audit. Nothing was built, flashed or run. Every row was checked by opening both sides.
Paths: `G` = `other-projects/otgw-6.6/gateway.asm`, `O` = `src/OTGW-firmware/OTDirect.ino`,
`L` = `src/libraries/OpenTherm/src/OpenTherm.cpp`, `S` = `docs/opentherm specification/OpenTherm-Protocol-Specification-v4.2.md` (in-repo, so the spec values below are verified in-repo).

Verdict words: same / different (bug candidate) / documented (ADR or code/c4 doc) / not implemented / unclear.

Spec values used (S): slave answer 20 / typ <100 / 400 ms (S:1094, S:1116), master wait time MWT 100 ms from the end of the previous conversation (S:1100), master communication interval MCI at most 1.15 s (S:1101, S:1116), gateway forwards within 7 ms (S:1124), software short-circuit = low voltage with no valid frame for at least 5 s, boiler acts within 15 s (S:1006-1016), bit period 900/1000/1150 us (S:814). Note: the user brief and the library comment (L:8) say "20 .. 800 ms"; the in-repo v4.2 says 400 ms.

### Bug candidates (survived skeptic pass), area C

**Bug 1 (Medium): one failed status exchange leaves the boiler without a frame for about 5-6 s in master mode (MCI 1.15 s, spec short-circuit window 5 s).**
- OTDirect: `handleMasterResponse` flips `bOnline = false` on any non-SUCCESS answer to MsgID 0 (O:1680-1689). `scheduleMasterRequest` then skips everything except MsgID 0 and retries it only every `OT_OFFLINE_RETRY_MS` = 5000 ms, counted from the send time (O:58, O:1731-1750, O:1778). Timeout alone costs 1 s (L:457-461), so the silence is about 5 to 6 s.
- PIC: no offline state. Standalone retries the same slot because `MessagePtr` does not advance without a matching answer (G:1490-1498) and `TickTimer` re-triggers every second (G:1549-1564). PIC's own comment at G:1702-1721 shows the author knew a silent master line turns into a heat demand.
- Spec: master must communicate at least every 1.15 s (S:1101); a boiler may treat low voltage with no valid frame for >= 5 s as a short circuit = heat demand, within 15 s (S:1006-1016). The ESP idle level equals the OT idle level; the PIC comment (G:1715-1716) says the default idle level is that low-voltage state.
- Failure scenario: master mode, SAT off, one status frame arrives with a parity error or the boiler is late once -> `bOnline = false` -> 5+ s of silence, only a queued command (SAT `CS=` resend every 5 s, ADR-207) could break it, and not at 1.15 s. A boiler with the optional software short-circuit detection can start a heat demand. Not verified on a boiler. Also the thermostat-present case is not affected (thermostat traffic is forwarded).
- Skeptic: checked that the offline flag really changes on a single failure (yes), that nothing else sends between (queue only, and it is empty without commands), that the 5 s is documented only as a code comment and c4 doc (`c4-code-otdirect.md:117`, ADR-208 mentions it as existing, no ADR decides it). Survives. Boiler reaction is the open part (bench).
- Suggested check: capture master-mode OT log, inject one corrupted status (or unplug the boiler 1 s), read the gap to the next frame.

**Bug 2 (Medium-Low, spec MWT): gap between the end of the boiler answer and the next own request can be 50-100 ms, spec says 100 ms.**
- Library: after a received frame `delayTimestamp = ts + RESPONSE_TIME * 1000`, `RESPONSE_TIME = 50` (L:8, L:443), enforced by `isReady()` (L:134-137). OTDirect gates the next own frame on `otMinIntervalMs` (default 100 ms) from the previous request START (O:1569, O:1717), and the scheduler only runs every 100 ms (O:2237).
- Timeline (own computation): request of 34 ms, boiler latency L (spec 20-400 ms), answer 34 ms -> answer ends at t+68+L. Tick t+100 fails the library gate for every L >= 0 (needs L <= -18). Tick t+200 passes when L <= 82 ms and then the gap is 132-L ms: 50 ms for L = 82, 82 ms for L = 50. Typical boilers answer "<100 ms" (S:1095).
- Spec: MWT 100 ms from the end of the previous conversation (S:1100). PIC standalone: >= 1 s between frames, so no issue there (G:1549-1573).
- Skeptic: MI is documented as "minimum inter-message gap" and defaults to 100 ms, which suggests the author equated MWT with request-to-request spacing; the library constant `RESPONSE_TIME` is upstream's. Not a protocol break that every boiler notices, but strict slaves may ignore or flag a request that arrives early. Survives as spec deviation; impact unmeasured. The library is vendored (no library edits per project rule), so a fix belongs in OTDirect (gate on response-end + 100 ms).
- Suggested check: otframes.log with timestamps from a master-mode capture, compute "B frame end -> next R frame start".

**Bug 3 (High if confirmed, needs bench): answers the gateway makes itself are sent immediately, but the slave object refuses to transmit for 50 ms after receiving a frame, and the return value is ignored.**
- Library: on DATA_READY the same `delayTimestamp = ts + 50 ms` is set for the slave object (L:443) and `sendResponse()` returns false while `isReady()` is false (L:294-312, L:136).
- OTDirect: `loopOTDirect` runs `otSlave.process()` (O:2147) and handles the pending frame in the same pass: master-mode answer `handleMasterModeSlaveFrame` -> `otSlave.sendResponse(response)` (O:2166-2169, O:2751), UI= Unknown-DataID (O:2200), SR= answer (O:2213), alt-slot Unknown-DataID (O:1875). None checks the result and `otSlaveFramePending` is cleared anyway. Only `replyToThermostat` checks and logs "reply to thermostat refused, slave not ready" (O:1484-1487), and that path is late enough (boiler answer >= 88 ms after the thermostat frame).
- PIC: its fake answers (SendAltResponse G:2463-2473) leave after the boiler answered the alternative, no hold-off.
- Failure scenario: thermostat on the bus, master mode (ADR-066 dual role), or UI=/SR= set, or an alternative slot (TASK-1707): the request reaches the boiler (alt slot) but the thermostat gets no reply, times out at 400 ms and retries (spec 4.5). Master mode with a thermostat would never get a single answer unless a loop pass lasts > 50 ms.
- Skeptic: could the loop be late enough? The pending frame is consumed in the same call as the DATA_READY, so the delta is microseconds. Could another layer queue the reply? No (grep of `sendResponse`: O:1484, 1875, 2200, 2213, 2751). Host tests use a mock whose `sendResponse` always returns true (`tests/test_otd_gateway_alt_slots.py:186`), so they cannot see it. TASK-1707 AC4 (bench with a thermostat) is still open, TASK-1178 note (d) already records the 50 ms gate for forwarded replies. Survives as "likely, unproven"; the real library was never exercised for these paths in this repo.
- Suggested check: bench with a thermostat (or the slave simulator), `UI=24` or master mode, watch for an `A` frame on the thermostat side and `OTD: ... refused` (not logged for these paths).

**Bug 4 (Low): MsgID 0 is starved for about 8 s once a minute in master mode (ADR-068 says every 800 ms).**
- `scheduleMasterRequest` returns the first due entry in table order starting after the last sent index (O:1736-1782). Status is index 0. The 81 slow entries (O:187-278) all become due together at uptime 60 s (all `lastSentMs = 0`, O:2523-2525) and stay 100 ms apart afterwards, so they are sent back to back (about 8.1 s) before the pointer wraps to index 0. Same, shorter (1.3 s), for the 13 ten-second reads.
- Not a spec violation (MCI is satisfied by the other frames) and PIC's own worst case is similar (9 s between its two status slots, see C3). The cost: CH/DHW enable changes (SAT CH=0, HW=) reach the boiler up to ~8 s late during that window. Plausible but not proven that the staggering persists in steady state; the first burst at uptime 60 s is certain. Survives as Low, and only as "behaviour does not match ADR-068 / c4 wording".

**Bug 5 (Low): fault code (ID5) is not read when the status shows a fault.** G:2751-2759 vs O:188 (60 s poll). The fault bit itself is visible at once (status every <= 0.8 s).

**Bug 6 (Low-Medium): MandatoryID exemption missing, and the `disabled` flag is sticky.**
- PIC un-blacklists IDs 0, 1, 3, 14, 17, 25 on every request (G:3383-3388, G:2712, G:2798, G:2959, G:3054, G:3623). OTDirect exempts only MsgID 0 (O:1622). Three Unknown-DataID answers in a row to ID 25, 17, 3, 1 or 14 disable the schedule entry for the rest of the session. Recovery only via `AA=`, `KI=`, `PM=`, mode switch or `GW=R` (O:2537).
- Additionally `clearUnknownCount()` on a success of the same ID relayed from the thermostat (O:1634-1637) does not clear `entry.disabled`, so counter and flag disagree (alt-slot logic uses the counter, scheduler uses the flag).
- Failure scenario: a boiler that answers Unknown-DataID to ID 17 or 25 while starting up or in a special state -> flow temperature / modulation polling stops for good; SAT and dashboards starve. Realistic frequency unknown; PIC added the exemption on purpose (comment G:3381-3382).

### Refuted / downgraded, area C

- R1 "OTDirect polls far more IDs than the PIC standalone, boiler overload": spec-legal at MWT, and the table is the documented design (ADR-068, c4 doc). Not a defect; only Bug 2 matters.
- R2 "3-strike differs from PIC": the numbers are identical (3 consecutive, 2 bits per ID, 0-127). Only the Data-Invalid detail differs, negligible.
- R3 "No TSet = 0 after CS=0 leaves the boiler heating": in master mode bit 0 (CH enable) is cleared when no CS override and no SAT (O:873), and OTDirect says CH= only takes effect with a CS override (O:823-831, PIC G:53 text cited there). With CH enable off the stale TSet should have no effect (not verified on a boiler). Kept in the table as "different, low", not a bug.
- R4 "AA=/DA= differ from PIC (re-enable/disable vs EEPROM list)": deliberate and commented (O:3411-3415); belongs to the command-parity audit.
- R5 "Handshake once at boot is a bug": the PIC never sends ID2/124/126 in standalone, so there is no parity defect; kept as C12 info.

### Bug candidates (survived skeptic pass), area D

**Bug 7 (Low-Medium): invalid frames and timeouts are invisible on OT-Direct.** No `E` frames, no "Error 0x", no counters, no debug line for INVALID/TIMEOUT other than the MsgID 0 offline transition (O:1680-1689; slave side O:673-679). PIC reports all four error classes (G:959-1000, G:1934-1943). `error01..04` values/HA sensors fed from `OTGW-Core.ino:6176-6195` stay at zero on these boards, which looks like "bus is clean". Impact: field reports ("no capture, no analysis" rule) cannot show line quality on OTGW32; cannot confirm Bug 1/2 effects. Skeptic: neither ADR nor c4 doc claims the error counters work on OTDirect (not checked whether the UI hides them); survives as "not implemented".

**Bug 8 (Low): frame validation weaker than the PIC.** Library accepts any 32-bit pattern whose stop-bit edge arrives and whose parity/type is valid; no stop-bit level check (PIC error02, G:714-715) and no mid-bit/transition-count check (PIC error01/03). Parity only catches an odd number of flipped bits. The 750 us edge filter (L:344-360) removes short glitches, so real-world risk is small. Survives as Low.

**Bug 9 (Medium-Low): thermostat loss leaves the boiler without frames for about 30 s.** In gateway mode with `bThermostatConnected` still true, `scheduleMasterRequest` returns immediately (O:1712, O:861-863) so nothing is sent until `checkThermostatTimeout` (1 s timer, `iSetbackTimeout` default 30 s) declares the thermostat gone (O:2654-2690). PIC notices an open line via ADC within tens of ms and sends its own frame within 1 s (G:1728-1816). The spec lets a boiler treat 5 s of silence as a heat demand and requires action within 15 s (S:1006-1016); the PIC comment G:1702-1721 documents exactly this hazard. Failure scenario: thermostat loses power or is unplugged -> about 15-30 s of possible unwanted heat demand before setback/own status take over. Not verified on a boiler; the default could be lowered (setting exists), which makes this a configuration/default question for Robert. ADR-066 explicitly chose protocol-level detection, but does not discuss the 30 s timeout or this window.

**Bug 10 (info): no on/off thermostat (short circuit) support.** PIC treats a shorted thermostat line as `HeatDemand`: TSet = max CH setpoint, CH enabled (G:1762-1765, G:2722, G:2806-2813). OTDirect has no input for it (no ADC use in `OTDirect.ino`). Not documented in ADR-063..066 or c4 doc (grep). "Not implemented"; relevant only if OTGW32 is sold for on/off thermostats.

### Refuted / downgraded, area D

- R6 "Bit timing differs": thresholds match (750 us, 500 us half bit). Refuted.
- R7 "20-800 ms response window is violated": the in-repo spec says 400 ms; OTDirect waits 1 s as master, i.e. tolerant, and the PIC enforces nothing. No defect, but the library comment (L:8) and the brief quote 800 ms; the v4.2 text in the repo says 400 ms. Doc discrepancy only.
