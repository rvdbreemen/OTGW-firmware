# Outbound connections on dev (TASK-1471)

Date: 2026-11-04. Base: worktree wt-1471, origin/dev 412a38e4d. Read-only audit, no firmware change, nothing run on a bench unit.

Scope: every connection the 2.0.0 ESP32-S3 firmware opens towards another host. Inbound servers (HTTP, WS, telnet, 25238), BLE and the PIC serial link are out of scope. File and line numbers are in `src/OTGW-firmware/` unless stated otherwise.

Evidence level: file:line facts were read in this session. Timeouts that come from the framework or lwIP (DNS, SNTP) were derived from the installed sources (arduino-esp32 3.3.5, ESP-IDF lwIP `dns.c`, `sntp_opts.h`) and are NOT measured on hardware. They are marked "derived". The bench (AC2) is what confirms them.

## 2. What blocks the loop task when the internet is blocked (AC3)

Facts that drive everything below:
- The loop task also runs SAT control, the OT frame consumer, MQTT pumping, and (because AsyncTCP is pinned to the same core, ADR-139) a long synchronous section starves HTTP and WebSocket. The PIC serial reader has its own task (`OTGW-Core.ino:935`), so PIC bytes are still collected, but they are consumed late.
- The loop task is on a 30 s TWDT with `trigger_panic = true` (`OTGW-Core.ino:1568-1573`). `[loop-stall] N ms gap` is printed for every gap above 200 ms (`OTGW-firmware.ino:1119`) and the maximum is `hd_max_loop_gap_ms` / `stats/max_loop_gap_ms`.
- DNS is not bounded by any HTTPClient timeout. `NetworkClient::connect(host, port, timeout)` calls `Network.hostByName()` first, which runs `lwip_getaddrinfo()` synchronously. Derived from lwIP `dns.c:1183-1210`: 1 s + 1 s + 2 s + 3 s = 7 s per configured DNS server before it gives up or moves to the next one.
- Quirk in the framework (arduino-esp32 3.3.5 `NetworkManager.cpp`, `hostByName` returns `err` on failure, which is non-zero and therefore truthy): `NetworkClient::connect(host, ...)` tests `!Network.hostByName(...)`, so after a failed lookup it still goes on and connects to 0.0.0.0 with the full connect timeout. Whether that costs 0 s or 5 s was not tested. The bench decides.

### Risky paths

R1. Weather fetch on the loop task (row 1). Blocks the loop for 5 s (SYN dropped) up to about 7-14 s plus up to 5 s (DNS blocked), at 300 s after boot and then 60, 120, 240, 480, 900 s. Not above the 30 s TWDT, but far above 1 s, and a retry storm of 5 stalls in the first 21 minutes. Logging and backoff are fine (once per interval, doubling to the 900 s cap). Minimal fix: run `weatherFetchOpenMeteo()` on a one-shot FreeRTOS task, same pattern as the webhook task (`webhook.ino:336`): `weatherLoop()` keeps the schedule and only sets a "fetch requested" flag, the task does DNS+GET+parse, writes `state.sat.weather` and clears an in-flight flag. Add `http.setConnectTimeout(2000)` as a second, independent bound. Do NOT try to shorten the DNS stall on the loop task, it cannot be bounded there.

R2. `refreshpic()` continues after a failed HEAD (row 4, `OTGW-Core.ino:6943-6946`). With the host unreachable it runs two blocked attempts back to back, about 34-48 s derived, which can exceed the 30 s TWDT and reboot the unit. User-triggered only, so rare, but it is a reboot path. Minimal fix: after `latest = checkforupdatepic(...)`, `if (latest.length() == 0) return;` (one line). Also add `feedWatchDog()` between DNS-blocking steps is not enough on its own, so the same task-based pattern as R1 is the proper fix for rows 3 and 4 (separate task, because the stall is unbounded).

R3. PIC update check on the loop task (row 3). Up to about 17-24 s derived per click, user-triggered, sticky ERROR result (no retry storm). Same fix as R2 (run it on the task). If the maintainer prefers KISS: leave rows 3 and 4 on the loop task, apply only the R2 one-liner, and record the stall as accepted because it needs a deliberate click.

R4. MQTT hostname lookup in `MQTT_STATE_INIT` (row 5). Only when the broker is a hostname and DNS itself is unreachable: about 7-14 s stall every 42-75 s. Does not apply to an IP-literal broker or to a LAN DNS server (the tester in the report redirects DNS to his own server). Minimal fix: remember the last good IP (`MQTTbrokerIP` is already a global) and on a failed lookup keep using it instead of going to ERROR; or move the lookup to the task from R1. Low priority.

R5. MQTT reconnect logging (rows 5-6). `[HEAP] pre-connect` / `post-connect-queue` (`MQTTstuff.ino:1369`, `:1385`) are not gated by the MQTT debug flag, so a down broker writes about 10 lines per cycle. Not a flood, and it concerns an unreachable broker rather than a blocked internet, but it does log on every attempt. Minimal fix: wrap both in `MQTTDebugTf`. Low priority.

R6. NTP (row 2). No loop impact. The only quirk is silence: in WAITFORSYNC there is no timeout and no failure line, so a blocked NTP leaves the clock unset without any log. Decision for the maintainer: that is arguably correct (no flood). If a hint is wanted, add one line after 10 minutes in WAITFORSYNC, logged once per `startNTP()`. No fix proposed by default.

Paths that already meet the AC (log once per retry interval, back off, no loop stall): NTP, webhook (own task, per edge, 3 x 30 s), mDNS/LLMNR. The PIC update check has no automatic retry at all.

Prediction for AC2: with the current code the weather path will show `[loop-stall]` gaps of 5 s or more, so the bench "no loop gap above the normal maximum" is expected to be RED until R1 is fixed. The bench run is the red evidence. AC3 asks for a fix or its own task for every failing path: R1 and R2 are the two that need one.

## 3. Bench plan for AC2

Rules from the task (Robert, 2026-11-04): one MikroTik rule per test, scoped to the bench unit, comment-tagged, scheduler auto-removal within 30 min, removed right after, config export before and after recorded in the task notes. The bench IPs are .63 (Classic + S3, has a PIC) and .61 (OTGW32, no PIC). MikroTik access: `ssh -i ~/.ssh/mikrotik admin@192.168.88.1`.

Preparation (once)
1. `/export file=t1471-before` on the router, copy it off, keep it for the notes.
2. Settings on the unit under test (save `curl http://<ip>/api/v2/settings` first and restore afterwards): `satweatherenable` on, coordinates set, `satweatherinterval` 900. Weather runs only when `OTcurrentSystemState.Toutside == 0`, so the unit must not receive an outside temperature from the OT bus (SAT outside source letter `W` in `SATcontrol.ino` ~2421 shows weather in use). Check the unit's DNS servers (`/api/v2/device` dns1/dns2): if the resolver is the router itself, a forward-chain rule does not touch DNS.
3. Baseline 15 min with no rule: telnet capture (`scripts/capture-mqtt-debug.bat -DeviceHost <ip> -BrokerHost 192.168.88.32 -DurationSeconds 900`), telnet key `z` first to zero `max_loop_gap_ms`. Record baseline max gap, free heap, SAT outside source.

Rule per test (RouterOS CLI; verify the scheduler behaviour with `print` before relying on it, the exact one-shot semantics were written from memory and not run)
- T1, SYN blackhole with DNS still answering (the case the task flags as not verified):
  `/ip firewall filter add chain=forward src-address=192.168.88.63 dst-address=!192.168.88.0/24 action=drop place-before=0 comment="TASK-1471-T1"`
  Optionally add `src-mac-address=AC:27:6E:CE:45:D8` to pin the MAC. `place-before=0` puts it first so fasttrack or an early accept cannot bypass it. Established flows may bypass a late filter, but all new outbound connections are matched.
- T2, rejected instead of dropped: same rule with `action=reject reject-with=icmp-network-unreachable` (comment "TASK-1471-T2"). Expect fast failure.
- T3, DNS itself blocked: T1 plus, in the input chain, `/ip firewall filter add chain=input src-address=192.168.88.63 protocol=udp dst-port=53 action=drop place-before=0 comment="TASK-1471-T3"` (and the same for tcp). Only valid when the unit's resolver is the router; otherwise the forward rule already blocks it.
- Auto-removal, armed in the same command batch, 30 min:
  `/system scheduler add name=t1471-rm interval=30m on-event="/ip firewall filter remove [find comment~\"TASK-1471\"]; /system scheduler remove [find name=t1471-rm]"`
  Prefer an explicit one-shot start (`start-date`/`start-time` from `/system clock print` plus 30 min, `interval=0`) if `print` shows the interval form fires immediately. Remove the rule by hand as soon as the observation is finished, then run `/export file=t1471-after` and diff against the before file.
